### Scenario A — simulated relay delivers

Observed, and it accidentally became the strongest evidence of the core
invariant available so far.

Event `9f701919` was created and persisted. Delivery then failed **eight
consecutive times** against a genuine, unanticipated fault: Android 9+ blocks
cleartext HTTP, so both the relay forward and the direct upload were rejected
by the platform. The log line on every one of those failures was
`event retained, still queued`.

The app was then **rebuilt and reinstalled** to add a network security config.
On relaunch:

```
BLE RELAY unavailable for 9f701919
ATTEMPT 9f701919 via SIMULATED RELAY (SIMULATED) attempt=9
SIMULATED relay rl_sim_relay_01 discovered 9f701919 (no radio involved)
SIMULATED relay accepted 9f701919 and is holding it
DELIVERED 9f701919 via SIMULATED RELAY
```

The emergency survived eight delivery failures **and** an application
reinstall, and was delivered on the ninth attempt. Backend record:
`sig_valid: true`, `first_delivery_path: "simulated_relay"`, `simulated: true`.

This was not a scripted scenario. It was a real failure, and nothing was lost.

### Scenario B — offline queue, then direct upload

1. *Relay in range* off, *force rider offline* on.
2. CREATE TEST SOS → event `d9559489` persisted and queued. Log showed all

3. *Force rider offline* off. Relay still absent.

### Bug found and fixed during this run

**Cleartext HTTP blocked on Android 9+.** Every delivery failed with
`Cleartext HTTP traffic to 10.0.2.2 not permitted`. Fixed by adding
`res/xml/network_security_config.xml` permitting cleartext to loopback and
private-LAN ranges only, with the base config still denying it. Documented as a
prototype constraint; a real deployment uses HTTPS and deletes that file.

This would have surfaced for the first time tomorrow morning, on hardware, with
the clock running.

## 2026-08-23 — BLE transport integration (no radio involved)

The BLE protocol was integrated behind the existing transport boundary. All of
the following is **codec and orchestration** testing on a JVM and an emulator;
none of it touches a radio.

- **Beacon codec** pinned byte-for-byte against the same vector the `:spike-ble`
  harness uses, which was itself generated from the Python backend. Product and
  spike stay interoperable, so during bring-up either side can be swapped in to
  isolate which one is at fault.
- **Packet round trip** — the exact operation a relay performs: encode on the
  rider, decode on the relay, verify the original signature, re-encode. The
  re-encoded bytes are asserted identical, which is what makes the relayed and
  direct paths idempotent at the backend.
- **Tamper rejection** — a modified packet still parses but fails verification,
  so a relay drops it rather than forwarding it. Without this, any nearby device
  could inject emergencies into the backend through an honest relay.
- **Privacy** — the 13-byte beacon is asserted to contain no raw event_id, no
  coordinate bit pattern and no rider id. This is T11's assertion in unit-test
  form; the over-the-air byte dump still has to be done on hardware.
- **Handoff semantics** — a relay ACK produces `RELAYED`, never `DELIVERED`, and
  the event stays pending so the rider keeps trying independently.
- **Schema migration v1 → v2** verified against a genuine v1 database on an
  emulator: a queued emergency, its `attemptCount`, its `lastError` and its
  audit trail all survive the upgrade.

### Observed in the running app *(emulated)*

- **S0 probe** produces the exact report that goes into this log tomorrow.
  On the emulator it reads `CAN ADVERTISE`, which is **worth nothing as
  evidence** — the emulated radio does not reflect a real chipset. It confirms
  the probe mechanism works, and nothing else.
- **Transport priority reordered** to direct-network first. When the rider is
  online, direct upload wins immediately and BLE never occupies the delivery
  window; when offline, its cheap connectivity check falls straight through.
  Observed: `ATTEMPT … via DIRECT NETWORK (REAL) attempt=1 → HTTP 201 →
  DELIVERED`.
- **A disarmed BLE transport cannot fake success.** With delivery pinned to
  BLE and `enabled = false`, an emergency was persisted, logged
  `BLE RELAY unavailable` on every pass, and the backend count did not move.
  The event stayed queued rather than being lost or falsely marked delivered.
- **Recovery after un-pinning:** restoring AUTO delivered that same queued
  event on the next pass, `DELIVERED … via DIRECT NETWORK`.

### Correction

An earlier reading of this session was wrong and is corrected here: the app
launching without a crash after the schema bump was taken as evidence that the
v1 → v2 migration had run on live data. It had not. AGP's
`connectedAndroidTest` uninstalls the app under test, so the database had been
wiped and was recreated fresh at v2 — confirmed by pulling the file and reading
`user_version = 2` with zero rows.

The migration is genuinely verified, but by `MigrationTest`, which builds a
real v1 database and migrates it forward. Not by that launch.

### Bug found and fixed during this work

`MigrationTestHelper` failed with
`AbstractMethodError: GeneratedSerializer.typeParametersSerializers()`. On the
androidTest classpath a BOM pinned `kotlinx-serialization-core` to 1.7.3 while
`room-testing` pulled `serialization-json` 1.8.1, and the newer json calls a
method the older core does not declare. Fixed by forcing the pair to the same
version, scoped to androidTest so the shipped app's resolution is untouched.

### What this does NOT prove

Nothing about BLE. No advertising, scanning, GATT connection, packet transfer
or acknowledgement has occurred over a radio. The codecs are proven; the
transport is not.
