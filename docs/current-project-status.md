the code and from test runs performed on that date, not from the plan.

| Term | Meaning |
|---|---|

| **UNKNOWN** | Not measured. No claim either way |

## 1. What the product currently does

A rider's phone confirms an emergency, signs it, and **writes it to disk before
attempting any delivery**. A background loop then tries each available transport
in priority order until one succeeds. If none does, the emergency stays on disk
and is retried — indefinitely, across process death and app reinstall.

Three transports exist behind one interface:

1. **Direct network** — the rider's own phone POSTs to the backend.
2. **BLE relay** — a nearby phone collects the emergency over Bluetooth LE and
   carries it. Implemented; **not validated on hardware**; disarmed by default.
3. **Simulated relay** — a development stand-in for a second phone. Records
   itself as `simulated_relay`, never as `ble_relay`.

A phone that collects someone else's emergency stores it and then uploads it
through the same delivery loop as its own. The backend is idempotent on
`event_id`, so the rider and any number of relays can all submit the same
emergency safely.

`RELAYED` and `DELIVERED` are separate states on purpose. A relay's
acknowledgement means another device has taken custody, not that the backend has
the event.

## 4. Emulator-only evidence

Obtained on AVD `roadlink_test` (Android 15, API 35, x86_64). Full detail in
[`verification-log.md`](verification-log.md).

- Persistence durability, 6 tests, on-disk Room closed and reopened between
  write and read.
- Schema migration v1 → v2 against a genuine v1 database, 2 tests.
- Scenario A (simulated relay delivers), Scenario B (offline queue then direct
  upload), Scenario D (duplicate submission → 1 event, 2 audit rows).
- The strongest single piece of evidence was unplanned: event `9f701919` was
  persisted, failed delivery **eight consecutive times** against a real platform
  fault (Android blocks cleartext HTTP), survived an application **rebuild and
  reinstall**, and was delivered on the ninth attempt with `sig_valid=true`.

Per `docs/phase1-spike-plan.md` §C.5, emulator results validate protocol logic
and code correctness only. They say nothing about radio behaviour, OEM battery
management, real permission prompts, RSSI or timing.

## 5. Not tested — physical devices

**No RoadLink BLE code has ever executed on a radio.** `BleRelayTransport.enabled`
is `false`, so the transport reports itself unavailable on every delivery pass.

The decisive unknown: whether `getBluetoothLeAdvertiser()` returns non-null on
the actual handsets. Central-only Android devices exist, and on those this
topology is impossible rather than merely slow.

The ladder that answers it is [`physical-ble-procedure.md`](physical-ble-procedure.md);
results go in [`physical-test-results.md`](physical-test-results.md), where every
cell currently reads NOT YET TESTED.

Also UNKNOWN, and not claimed anywhere: BLE range, discovery latency, relay
success rate, battery cost, background/screen-off behaviour, OEM-specific
behaviour, GPS accuracy in the field (the emulator had no fix, so every emulated
event carried a null position — the no-location path is exercised, the
with-location path is not).

## 8. Known defects

None outstanding. Two have been found and fixed, both recorded in
[`verification-log.md`](verification-log.md):

**An emergency interrupted mid-delivery was never delivered** (found 2026-08-28).
An event is written to disk in `DELIVERY_ATTEMPT` before the transport is
called, so that is its on-disk state for the whole duration of a transport call
- a five-second connect timeout, a twenty-second advertising window. Killed
inside that window, the event could not legally re-enter `DELIVERY_ATTEMPT` on
the next launch, so the delivery pass threw on it and aborted; because pending
events are ordered oldest-first, one stranded emergency stopped every newer one
being attempted too. Nothing was lost, but nothing was delivered either. Fixed
by recovering an interrupted event to `QUEUED_OFFLINE` before any attempt,
recording the interruption as `INTERRUPTED` rather than as a failure, and
isolating each event in a pass. Five tests in `DeliveryRecoveryTest`.

**Unbounded audit-trail growth while offline.** A transport reporting itself
unavailable was never tried, so it did not advance the attempt count and did not
consume backoff — meaning the delivery loop appended an identical audit row per
transport per pass (roughly three rows every three seconds per queued
emergency), growing without bound during exactly the offline stretch the product
exists for, and burying the informative rows. Fixed by recording the first
occurrence and suppressing repeats until the reason changes; availability is
still re-checked every pass, so delivery still resumes the instant a transport
returns. Covered by two new tests in `DeliveryScenarioTest`.

## 10. Recommended final scope

**Lead with durable offline delivery, present BLE as an implemented but
unvalidated extension.** The offline-queue → reconnect → direct-upload path is
demonstrable today and is a complete story on its own. That framing survives the
BLE hardware test failing, which the current evidence cannot rule out.

Do, in order:

1. Run the physical BLE ladder if two phones are available. If T5 and T6 pass,
   promote BLE to a demonstrated capability with its measured success rate and
   sample size. If they fail, record that and change nothing else — the demo
   does not depend on it.
2. Record the demo video against Scenario B.
3. Build the deck from [`architecture.md`](architecture.md) and this document.

Do **not**: add sensor crash detection, multi-hop mesh, or any dispatch
integration before the submission. None of them can be tested in the time
available, and claiming them would be dishonest.
